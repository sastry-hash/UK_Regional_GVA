# Technical Challenges and Solutions

## UK Regional GVA Data Warehouse & Power BI Analytics

### Overview

During the development of this project, I encountered several technical challenges involving data ingestion, SQL Server memory management, data quality, dimensional modelling and Power BI reporting.

This document explains the problems, their causes, the solutions implemented and the technical lessons learned.

**Technology stack:** SQL Server, T-SQL, Python, Pandas, Power BI, DAX and GitHub.

## Challenge 1: CSV Delimiter and SQL Server Bulk Import Errors

### Problem

During the initial Bronze-layer ingestion, I attempted to import the prepared ONS regional GVA dataset into SQL Server using `BULK INSERT`.

The source data contained industry descriptions with embedded commas. When the file was treated as a simple comma-delimited dataset without appropriate handling of quoted fields, SQL Server encountered parsing and data conversion problems.

### Root Cause

The CSV structure contained text values that included commas, causing incorrect column separation during ingestion.

For example, an industry description such as:

`Wholesale and retail trade, repair of motor vehicles`

contains a comma that should be interpreted as part of the text rather than as a column separator.

### Solution

I used Python and Pandas to prepare the dataset and export it using a pipe (`|`) delimiter.

Example:

```python
df.to_csv(
    "regional_gva_cleaned_pipe.csv",
    sep="|",
    index=False,
    encoding="utf-8"
)
```

The resulting file could then be imported using the appropriate SQL Server bulk-loading configuration.

```sql
BULK INSERT bronze.RegionalGVA_Raw
FROM 'C:\Data\regional_gva_cleaned_pipe.csv'
WITH
(
    FIELDTERMINATOR = '|',
    ROWTERMINATOR = '0x0a',
    FIRSTROW = 2,
    CODEPAGE = '65001'
);
```

The file path must be adjusted for the SQL Server environment.

### Outcome

The revised file format resolved the delimiter-related ingestion issue and enabled the prepared dataset to be loaded into the Bronze layer.

### Key Learning

Reliable data ingestion requires understanding source-file formatting, encoding, delimiters and the target database schema.

## Challenge 2: SQL Server Memory Limitations During Silver Transformation

### Problem

During the Bronze-to-Silver transformation, I initially attempted to process the dataset using a single large insert operation.

SQL Server returned an insufficient buffer pool memory error.

### Root Cause

The transformation approach required SQL Server to process a substantial operation in one execution, creating memory pressure in the available database environment.

### Solution

I changed the transformation process to load records in smaller batches of approximately 5,000 rows.

Illustrative T-SQL logic:

```sql
DECLARE @BatchSize INT = 5000;
DECLARE @StartRow INT = 1;

WHILE @StartRow <= @MaxRow
BEGIN

    INSERT INTO silver.RegionalGVA_Clean
    (
        ITLCode,
        RegionName,
        GeographyLevel,
        SIC07Code,
        SIC07Description,
        IndustryLevel,
        [Year],
        GVAMillionGBP
    )

    SELECT
        ITLCode,
        RegionName,
        GeographyLevel,
        SIC07Code,
        SIC07Description,
        IndustryLevel,
        [Year],
        GVAMillionGBP

    FROM #SilverStage

    WHERE RowNum BETWEEN
        @StartRow AND (@StartRow + @BatchSize - 1);

    SET @StartRow = @StartRow + @BatchSize;

END;
```

The full transformation script is available in `sql/03_silver_transform.sql`.

### Outcome

Batch-based processing allowed the Silver transformation to complete within the available SQL Server resources.

### Key Learning

ETL design should account for infrastructure constraints. Batch processing can reduce resource pressure and improve operational reliability.

## Challenge 3: Duplicate Records During Repeated Data Loads

### Problem

During pipeline development and testing, repeated data-loading operations introduced the risk of duplicate observations.

Duplicate records could inflate GVA totals and affect downstream Power BI calculations.

### Root Cause

Re-running insert operations without appropriate duplicate checks can create repeated business records.

### Solution

I introduced duplicate validation using the expected business key:

`ITLCode + SIC07Code + Year`

Example:

```sql
SELECT
    ITLCode,
    SIC07Code,
    [Year],
    COUNT(*) AS DuplicateCount

FROM silver.RegionalGVA_Clean

GROUP BY
    ITLCode,
    SIC07Code,
    [Year]

HAVING COUNT(*) > 1;
```

The Gold fact table design also includes a unique constraint on its three dimensional foreign keys.

### Outcome

Duplicate validation became part of the data quality process, helping ensure that repeated loads did not silently create duplicate analytical observations.

### Key Learning

Data pipelines should be designed with repeatability and idempotency in mind.

## Challenge 4: Incorrect GVA Totals Caused by Hierarchical Aggregation

### Problem

During Power BI dashboard development, some GVA totals appeared substantially higher than expected.

The issue required investigation of the underlying data model, classification levels and aggregation logic.

### Root Cause

The dataset includes multiple levels of industry and geographic aggregation.

Industry classifications include:

- TOTAL
- SECTOR
- SECTION
- SUBSECTION
- DIVISION
- SPECIAL

Summing values from overlapping classification levels can count the same economic activity multiple times.

Similarly, combining geographic totals with their constituent regions can inflate results.

### Solution

I reviewed the source classifications, SQL analytical model and Power BI filtering logic.

The dimensional model retains `IndustryLevel` and `GeographyLevel`, allowing the dashboard to distinguish between different levels of aggregation.

For example, division-level comparisons can be restricted using:

```sql
WHERE IndustryLevel = 'DIVISION'
```

Headline GVA calculations require identifying the appropriate single overall-GVA classification rather than summing every total or subtotal.

### Outcome

The investigation identified hierarchy-aware filtering as an essential requirement for accurate reporting.

### Key Learning

Correct SQL syntax does not guarantee correct business results. Understanding data granularity, hierarchy and aggregation rules is essential for trustworthy analytics.

## Challenge 5: Power BI DAX Percentage Formatting

### Problem

During dashboard development, some percentage measures displayed unexpected values, including values rounded to `0.0%`.

This created difficulty when interpreting economic growth and recovery indicators.

### Root Cause

DAX calculations and Power BI display formatting must be consistent.

For example, a measure returning `0.0037` represents `0.37%` when formatted as a percentage.

Incorrect formatting or excessive rounding can make a valid calculation appear misleading.

### Solution

I reviewed the DAX measures and configured the appropriate percentage formatting.

Example:

```dax
YoY Growth % =
DIVIDE(
    [YoY GVA Change (£m)],
    [Previous Year GVA (£m)]
)
```

The measure should be formatted as **Percentage** with an appropriate number of decimal places.

### Outcome

The dashboard measures became easier to interpret and more consistent with the intended economic indicators.

### Key Learning

BI development requires validating both calculation logic and how results are presented to end users.

## Challenge 6: Power BI Slicer and Visual Interaction Issues

### Problem

During dashboard development, some slicers and visualisations did not initially respond as expected.

In particular, regional, industry and year selections required careful configuration to ensure that charts displayed the intended data.

### Root Cause

Power BI filtering depends on relationships, filter context and visual interactions.

An unexpected slicer result can arise from incorrect field selection, overlapping filters or unsuitable visual interaction settings.

### Solution

I reviewed:

1. Fact-to-dimension relationships.
2. Fields used in slicers.
3. Visual-level and page-level filters.
4. Power BI Edit Interactions settings.
5. DAX measures under different filter selections.

I also tested the dashboard using specific regions, industries and reporting years to verify that the visualisations responded appropriately.

### Outcome

The dashboard interaction behaviour was reviewed and adjusted to support more consistent filtering across report pages.

### Key Learning

Interactive BI dashboards require testing of relationships, measures and user-facing filtering behaviour, not just visual design.

## Challenge 7: Maintaining Consistent Dimensional Relationships

### Problem

The source dataset contains region codes, SIC07 codes, reporting years and numerical GVA observations in a single structure.

Using this structure directly for all reporting calculations can make the model harder to maintain and validate.

### Solution

I designed a Gold-layer star schema with:

- `gold.DimRegion`
- `gold.DimIndustry`
- `gold.DimDate`
- `gold.FactRegionalGVA`

The fact table connects to the three dimensions using surrogate keys.

This separates descriptive attributes from numerical observations and provides a structured model for Power BI.

### Outcome

The dimensional model supports reusable relationships, consistent filtering and clearer analytical calculations.

### Key Learning

Dimensional modelling improves the organisation and maintainability of analytical datasets and helps establish clear reporting granularity.
